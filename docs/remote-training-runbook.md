# Remote Data Audit and TFT Candidate Training Runbook

For the current Ubuntu/SSH host audit and preflight checklist, see
[`docs/ubuntu-training-audit.md`](ubuntu-training-audit.md).

This runbook covers the current three-machine workflow:

- `John_Surface`: Windows 11 Surface Pro 11 with WSL2 Ubuntu 22.04. It was the
  first development environment through handoff commit
  [`3f1218b`](https://github.com/yorkjohn/PolyWeatherBot/commit/3f1218ba0abb616dfbeac7754c330693f82a395c).
  It now acts mainly as the operator workstation, using VS Code Remote SSH into
  `john_linux`.
- `john_linux`: trusted Ubuntu 22.04 LAN host with an RTX 2060. It has the full
  private repository and is the primary machine for development, deployment,
  weather download, data audit, TFT training, model review/promotion, and
  production.
- `john_server`: Windows host with WSL2 Ubuntu 22.04 and an RTX 5090. It is a
  high-power, lower-trust, shared-use machine. It cannot be reached by SSH in
  the current workflow and is only an optional large-scale training worker.

`john_linux` is the trusted authority for review, import, explicit promotion,
and production. `john_server` may produce candidate training outputs only; it
must not receive production secrets, production DB state, or production
activation authority.

## 0. Rules

- All internal timestamps are UTC.
- `start`, `end`, `train`, `val`, and `test` dates are UTC dates.
- `init_time`, `valid_time`, `created_at`, `started_at`, `finished_at`, and
  `tick_utc` must be timezone-aware UTC values.
- Training commands must not implicitly write production `active_version.txt`.
- DBs produced by training-only runs are evidence only, not a state source.
- Production consumes only reviewed `hrrr/`, `obs/`, and active model artifacts.
- Production must not consume `_decoder_cache`.
- `john_linux` can use the full repo. `john_server` should use only the minimal
  training bundle generated by `scripts.build_remote_training_bundle`.
- Never copy `.env`, production private keys, production DB state, or production
  `active_version.txt` to `john_server`.

## 1. Initialize john_linux

SSH into the remote server:

```bash
ssh <user>@john_linux
```

Clone and enter the repo:

```bash
mkdir -p ~/polyweather
cd ~/polyweather
git clone <your-repo-url> PolyWeatherBot
cd PolyWeatherBot
```

Checkout the approved commit or tag:

```bash
git fetch --all --tags
git checkout <approved_commit_or_tag>
git status --short
git rev-parse HEAD
```

`git status --short` should be empty. If it is not empty, do not use this run
for formal training unless you intentionally accept a dirty run and record it.

Create the Python environment:

```bash
python3 -m venv .venv
. .venv/bin/activate
python -m pip install -U pip
python -m pip install -e .
```

Verify training dependencies:

```bash
python -c "import torch, lightning, pytorch_forecasting, zarr, s3fs; print('training deps ok')"
```

Optional environment evidence:

```bash
python --version
python -m pip freeze > remote_pip_freeze.txt
nvidia-smi || true
```

## 1A. Optional: Prepare `john_server` Training-Only Code

Use this only when you want to use the RTX 5090 on `john_server` for a large
training run. Build the minimal bundle on `john_linux`, not on `john_server`:

```bash
cd /home/john/Work/PolyWeatherBot
mkdir -p dist
./.venv/bin/python -m scripts.build_remote_training_bundle \
  --output dist/polyweather-training-bundle-$(git rev-parse --short HEAD).tar.gz
sha256sum dist/polyweather-training-bundle-*.tar.gz
```

The bundle is a source whitelist for training only. It includes:

```text
config/
db/schema.py
data manager, cleaners, parquet store
model features, TFT, training data, registry
scripts/run_remote_training.py
scripts/train_tft.py
```

It excludes:

```text

events/
snipers/
ui/
backtest/
tests/
docs/
data/clob/
model/pipeline.py
scripts/seed_demo_data.py

scripts/batch_prepare_training_data.py
scripts/smoke_bootstrap.py
scripts/audit_training_data.py
scripts/audit_weather_backfill.py
.env
```

Transfer the bundle to `john_server` through the available remote-control or
manual file-transfer path. `john_server` is not reachable by SSH in the current
workflow, so do not plan around `scp` or remote shell automation.

After the bundle is present on `john_server`, run these commands inside the
`john_server` WSL2 Ubuntu shell:

```bash
mkdir -p ~/polyweather-server
cd ~/polyweather-server
mkdir -p PolyWeatherBot
tar -xzf polyweather-training-bundle-<commit>.tar.gz -C PolyWeatherBot
cd PolyWeatherBot
python3 -m venv .venv
. .venv/bin/activate
python -m pip install -U pip
python -m pip install -e .
python -c "import torch, lightning, pytorch_forecasting; print('john_server training deps ok')"
```

`john_server` still needs training data. The preferred path is:

1. Download and audit on `john_linux`.
2. Export a training-input tarball from `john_linux`.
3. Copy that tarball to `john_server`.
4. Run only `train` and `package` on `john_server`.

On `john_linux`, after audit passes:

```bash
./.venv/bin/python -m scripts.run_remote_training export-lab-input \
  --run-root runs \
  --run-id "$RUN_ID"
sha256sum runs/$RUN_ID/artifacts/${RUN_ID}_lab_training_input.tar.gz
```

Transfer the generated lab-training input tarball to `john_server` through the
same remote-control/manual file-transfer path. This tarball contains
`_decoder_cache` because `john_server` needs it to train. It is not a
production weather data package.

On `john_server`:

```bash
mkdir -p runs/$RUN_ID
tar -xzf ${RUN_ID}_lab_training_input.tar.gz -C runs/$RUN_ID

python -m scripts.run_remote_training train \
  --run-root runs \
  --run-id "$RUN_ID" \
  --station "$STATION" \
  --version tft_20260608_klga_5090_try01 \
  --train 2026-04-08:2026-05-20 \
  --val 2026-05-21:2026-05-27 \
  --test 2026-05-28:2026-06-04 \
  --min-epochs 5 \
  --max-epochs 20 \
  --batch-size 64 \
  --seed 42 \
  --deterministic \
  --precision 32 \
  --num-workers 0

python -m scripts.run_remote_training package \
  --run-root runs \
  --run-id "$RUN_ID" \
  --version tft_20260608_klga_5090_try01 \
  --model-only
```

Transfer only the candidate model package, manifest, audit, and train result
back from `john_server` to `john_linux`. Do not promote on `john_server`.

## 2. Plan The Run

Choose a run id and model version:

```bash
export RUN_ID=tft_20260608_klga_apr_jun
export VERSION=tft_20260608_klga_apr_jun
export STATION=KLGA
```

Example date plan:

```text
download range: 2026-04-01 .. 2026-06-04
train:          2026-04-08 .. 2026-05-20
val:            2026-05-21 .. 2026-05-27
test:           2026-05-28 .. 2026-06-04
```

Keep enough cold-start history before the train split. For example, if download
starts on 2026-04-01, starting train on 2026-04-08 leaves enough room for the
72-hour encoder window.

## 3. Run Stages On john_linux

The remote command is staged. Use `all` for a first end-to-end smoke/initial
run. For normal experimentation, run `download` once, then rerun `audit`,
`train`, and `package` as needed.

### 3.1 First Full Run

```bash
. .venv/bin/activate

python -m scripts.run_remote_training all \
  --run-root runs \
  --run-id "$RUN_ID" \
  --station "$STATION" \
  --start 2026-04-01 \
  --end 2026-06-04 \
  --train 2026-04-08:2026-05-20 \
  --val 2026-05-21:2026-05-27 \
  --test 2026-05-28:2026-06-04 \
  --version "$VERSION" \
  --workers 12 \
  --min-epochs 1 \
  --max-epochs 1 \
  --batch-size 16 \
  --seed 42 \
  --deterministic \
  --precision 32 \
  --num-workers 0
```

The `all` command performs:

1. Create `runs/<RUN_ID>/`.
2. Download HRRR f01 into `runs/<RUN_ID>/data_store/hrrr`.
3. Download and clean IEM into `runs/<RUN_ID>/data_store/obs`.
4. Warm training decoder cache into `runs/<RUN_ID>/data_store/_decoder_cache`.
5. Run pre-training data audit.
6. Train TFT only if audit passes.
7. Generate a candidate model package.
8. Generate a production weather data package.

For repeated hyperparameter experiments on `john_linux`, skip `download` and
rerun only `train` plus `package`. For `john_server`, do not run `download`
unless you intentionally trust that machine with the full data acquisition
workflow; prefer the training-input tarball from `john_linux`.

### 3.2 Download And Clean Only

Use this when the data range is new, or when a previous download had gaps:

```bash
python -m scripts.run_remote_training download \
  --run-root runs \
  --run-id "$RUN_ID" \
  --station "$STATION" \
  --start 2026-04-01 \
  --end 2026-06-04 \
  --workers 12
```

This writes:

```text
runs/<RUN_ID>/data_store/hrrr/
runs/<RUN_ID>/data_store/obs/
runs/<RUN_ID>/data_store/_decoder_cache/
runs/<RUN_ID>/download_summary.json
runs/<RUN_ID>/stage_state.json
```

This stage is safe to rerun. Existing parquet/cache files are reused where the
underlying stores support it.

### 3.3 Audit Only

Use this after download, or after manually fixing missing data:

```bash
python -m scripts.run_remote_training audit \
  --run-root runs \
  --run-id "$RUN_ID" \
  --station "$STATION" \
  --train 2026-04-08:2026-05-20 \
  --val 2026-05-21:2026-05-27 \
  --test 2026-05-28:2026-06-04
```

This writes:

```text
runs/<RUN_ID>/audit_summary.json
runs/<RUN_ID>/failed_audit_summary.json   # only when audit fails
runs/<RUN_ID>/stage_state.json
```

Training must not start unless `audit_summary.json` has `ready: true`.

### 3.4 Train Only

Use this for repeated hyperparameter experiments. It does not download data:

```bash
python -m scripts.run_remote_training train \
  --run-root runs \
  --run-id "$RUN_ID" \
  --station "$STATION" \
  --version tft_20260608_klga_try02 \
  --train 2026-04-08:2026-05-20 \
  --val 2026-05-21:2026-05-27 \
  --test 2026-05-28:2026-06-04 \
  --min-epochs 5 \
  --max-epochs 20 \
  --batch-size 32 \
  --seed 42 \
  --deterministic \
  --precision 32 \
  --num-workers 0
```

This requires an existing `audit_summary.json` with `ready: true`.

This writes:

```text
runs/<RUN_ID>/model_store/<VERSION>/
runs/<RUN_ID>/checkpoints/
runs/<RUN_ID>/polyweather.db
runs/<RUN_ID>/train_result.json
runs/<RUN_ID>/stage_state.json
```

Use a new `--version` for each material hyperparameter experiment.

### 3.5 Package Only

Use this after training, or if you need to regenerate artifacts:

```bash
python -m scripts.run_remote_training package \
  --run-root runs \
  --run-id "$RUN_ID" \
  --version tft_20260608_klga_try02
```

On `john_server`, add `--model-only` to generate only the candidate model
package and skip `production_weather_data.tar.gz`.

This writes:

```text
runs/<RUN_ID>/artifacts/<VERSION>.tar.gz
runs/<RUN_ID>/artifacts/production_weather_data.tar.gz
runs/<RUN_ID>/weather_data_manifest.json
runs/<RUN_ID>/manifest.json
runs/<RUN_ID>/stage_state.json
```

Expected run layout:

```text
runs/<RUN_ID>/
  data_store/
    hrrr/
    obs/
    _decoder_cache/          # training-only; not production data
  model_store/
    <VERSION>/
      model.ckpt
      training_dataset.pkl
      meta.json
      training_metadata.json
      train_result.json
  checkpoints/
  polyweather.db             # training evidence DB, not production state
  download_summary.json
  audit_summary.json
  train_result.json
  manifest.json
  stage_state.json
  artifacts/
    <VERSION>.tar.gz

```

## 4. If Audit Fails

If data is incomplete, the run stops before training. Inspect:

```bash
cat runs/$RUN_ID/failed_audit_summary.json
cat runs/$RUN_ID/audit_summary.json
```

Look for:

```json
{
  "ready": false,
  "failures": []
}
```

Common causes:

- Missing HRRR f01 hours.
- Missing IEM obs hours.
- Missing decoder cache init windows.
- A train/val/test split cannot build 120 rows per init.
- Required TFT columns are missing.
- Required TFT inputs contain NaN.

Usually, rerun `download` if source data was missing, then rerun `audit`.
Do not rerun `train` until audit is ready.

## 14. Flow Summary

```text
John_Surface operates VS Code Remote SSH into john_linux
  -> john_linux maintains the working checkout
  -> john_linux checkout approved commit
  -> john_linux download HRRR/IEM/decoder
  -> john_linux clean and audit
  -> john_linux train TFT, or export audited training input to `john_server`
  -> `john_server` optionally trains from minimal bundle + audited data
  -> training machine packages candidate model
  -> john_linux packages reviewed hrrr/obs weather data when needed
  -> john_server outputs are manually transferred back to john_linux when used
  -> john_linux reviews manifest/audit/metadata
  -> john_linux imports candidate
  -> john_linux evaluates
  -> john_linux promotes explicitly
  -> john_linux or another production host consumes active model + hrrr/obs
```

john_linux can produce candidates and later run production, but activation is
still explicit. `john_server` can produce candidates only. It cannot decide
production activation.
